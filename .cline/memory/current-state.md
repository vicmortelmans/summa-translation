# Current state

## Implemented

- Six-stage batch workflow (`batch_workflow.sh`):
  input → references → glossary → translation → merge → inventory +
  consistency analysis. The final stage writes
  `<job>/glossary-application-inventory.csv` and `<run>/glossary-consistency/`
  (`report.md`, `report.html`, CSVs incl.
  `inter-batch-lemmata-disambiguation.csv`, `summary.json`).
- `batch_merge.py` merges all translation batches of a job into
  `<job>/40-merge/translations.json`, accumulates token counts per category
  into `<job>/40-merge/tokens.json`, and logs its command line to
  `<job>/40-merge/batch_merge_command.txt`. It accepts `--tag <tag>` or a
  positional job name/path.
- `batch_glossary.py` builds per-sentence glossary entries from the Axters
  lexicon using CLTK lemmatization and writes them to `<job>/25_glossary/`.
  Output objects keep all input fields and add
  `glossary: [{source, lemma, definitions}]`, where `definitions` is an ordered
  list of Dutch senses. Exact headword matches use one entry; ambiguous CLTK
  lemmas merge all their definitions (shortest list first, round-robin).
- `prompts/translate.txt` documents how to use references and glossaries,
  including the first-definition bias and cross-sentence consistency rule.
- `axters-mistral/axters-scholastiek-lexicon-1937-cltk.json` (lemma, cltk,
  definition) is tracked in git and generated by
  `axters-mistral/lemmatize_axters.py`.
- `glossary_application_inventory.py` writes a per-sentence/per-glossary-entry
  CSV for a finished run (`<run>/glossary-application-inventory.csv`), keyed by
  the JSON sentence id and including the number of glossary alternatives,
  matching the proposed Dutch definitions against the translation with
  conservative inflection rules (first definition wins; 0 when another rendering
  is used). Verified on `run-glossary`: 4,409 sentences, 27,192 entries, 18,697
  (68.8%) matched a proposed definition.
- `analysis-glossary-consistency/scripts/analyse_glossary_consistency.py`
  finds lemmas rendered consistently within batches but differently across
  batches. It reads the inventory plus `30_translation/`, applies configurable
  occurrence/purity/batch thresholds, and writes ranked CSVs, a JSON summary and
  an HTML report with batch charts and corpus timelines to
  `<run>/glossary-consistency/`. On `run-glossary` the default thresholds yield
  5 candidates (beatitudo, operatio, philosophus, opus, accido1), with
  `beatitudo` the clear priority (153 of 401 qualifying occurrences switched).
- Work committed through HEAD (`cc1892d merge`); the glossary rework in
  `batch_glossary.py` (exact-match/merge, then the `definitions` list), the
  `batch_workflow.sh` stage 6, the wider `25_glossary/*.json` glob in
  `glossary_application_inventory.py`, the prompt update and the
  analysis-script compatibility changes are uncommitted in the worktree at the
  time of writing. Other untracked scratch files remain (`__pycache__/`,
  `align/.latin.stem.swp`, extra TSVs, analysis directories).

- Terminology harmonisation workflow (`terminology_workflow.sh` +
  `terminology_plan.py`, `terminology_apply.py`, `terminology_verify.py`,
  `terminology_common.py`, `terminology_forms.py`,
  `terminology_form_inventory.py`): reads the reviewed
  `inter-batch-lemmata-disambiguation.csv` (`lemma,translation,forms,note`),
  plans only non-conforming sentences, calls `batch_translate.py` with
  `schemas/terminology_review.schema.json` and
  `prompts/terminology-review.txt`, applies the revisions per lemma into
  `run-<tag>/50-terminology/30_translation/`, writes changes/exceptions/summary
  reports, merges, and re-runs the inventory/analysis on the corrected layer.
- Stage 7 of `batch_workflow.sh` writes
  `glossary-consistency/lemma_form_inventory.csv` (every Latin form of every
  candidate lemma, with counts). The analysis CSV header is now
  `lemma,translation,forms,note`.
- `glossary_application_inventory.py` accepts `--glossary-dir` and
  `--translation-dir`; `analyse_glossary_consistency.py` accepts `--inventory`
  and `--translation-dir`. Defaults are unchanged.

## Known limitations / open questions

- Glossary lookups only match exact normalized forms. Multi-word lexicon keys
  and lemmatizer outputs absent from the lexicon are skipped (e.g.
  `principia`, `interiora` in the sample sentence were not matched).
- Ambiguous CLTK lemmas merge definitions from entries that may belong to
  different parts of speech, so common verbs get noisy merged senses (`sum` →
  `toekomstig, zijn, toekomst, aanzijn, het toekomstige`; `dico` →
  `zegging, zeggen, verwoorden`). This is an accepted consequence of the rule
  that none of the entries is primary.
- The `lemma` field is the raw CLTK output and can contain artefacts such as
  `sum` (for forms of *esse*) or homonym markers like `cum2`.
- Every matched word is included, including common function words
  (`per`, `quia`, `magis`). Whether the glossary should be limited to
  scholastic/technical terms has not been decided.
- `cltk` is installed in `./env` but missing from `requirements.txt`; rebuilding
  the environment from that file alone will break the glossary stage.
- Glossary files produced before the `definitions` change use the legacy
  comma-separated `translation` string. `glossary_application_inventory.py`
  and `analysis-20261115-terminology` accept both shapes; any other consumer
  of `25_glossary` JSON must read `definitions` (list) for new runs.
